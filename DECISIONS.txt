#1 Flyway migrations with ddl-auto=validate
Why: Flyway is the source of truth so having ddl-auto=validate makes sure Hibernate does not modify, update, or delete the schema

#2 Postgres in Docker Compose on host port 5433
Why: I already had PostgreSQL 18 using port 5432 so using a different port allows both to run at once

#3 Config from environment variables
Why: .env is used to store passwords and credentials. The same code is able to run on my laptop and AWS by only changing the environment values. .env.example is also included as an example

#4 TIMESTAMPTZ instead of TIMESTAMP
Why: TIMESTAMPTZ converts the time to UTC while TIMESTAMP does not. With TIMESTAMP, 9:00 AM in Singapore and 9:00 AM in New York look identical. TIMESTAMPTZ prevents issues with comparisons like if a link has expired.

#5 One row per click instead of a counter on links
Why: This allows better metrics like how many clicks on each day and where each click came from.

#6 ON DELETE CASCADE
Why: Once a link is deleted, the clicks associated with it no longer matter as the data and metrics cannot be used anymore.

#7 How to generate the short codes
Context:
	7 characters from Base62 (a-z,A-Z,0-9) is ~3.52 Trillion combinations so collisions are very rare
	Randomness comes from the SecureRandom (java.security) instead of Random because Random is predictable
Considered:
	Encode the database ID in Base62
	Generate a random code
	Hash the long URL and keep the first few characters
Decision: Generate a random code
Why:
	Encoding the database ID in Base62 makes it possible for a user to walk through each link. This is too predictable
	Hashing means the same URL always gets the same code, so two users tracking the same page would share one link and one click history. Different URLs could also collide.
	Generating a random code solves this issue. Each user gets a unique code because the code column is UNIQUE. This means the database rejects duplicates so I retry if the generated code is not accepted. Two links would have two different codes so each user gets their own metrics.

#8 301 or 302 redirects
Decision: 302 redirects
Why:
    301 redirects are cached by the browser. Tracking clicks would be ineffective because after the first click, using the url in the future bypasses the server and I would not be able to track the number of clicks. The downside of using 302 is that the user goes through the server every time which is additional load. 301 redirects would reduce the number of requests and would be the right choice if I was not tracking anything.

#9 File structure
Considered:
    Layers like controller, service, repository, model, and dto
    One folder per feature like link/
Decision: Layers
Why:
    I believe separating by features is better for larger applications but for an application with a few features I believe separating the layers will be more effective. This is because with only a few features, a layered folder structure keeps the number of folders small and classes of the same kind sit in the same place. My thought process also looks at the application in layers so the folder structure aligns with my view.

#10 Token design: Token Length
Considered: 
	7 base62 chars, 12 base62 chars, 32 bytes
Decision: 32 bytes
Why:
	Using a token length the same as the short url code would not work because the number of combinations is guessable. 12 base62 chars is around 71 bits which holds up today but is not future proof against the 128 bits that security guidance recommends. The chosen hash function is SHA-256 and its possible to run through billions of combinations per second. 32 random bytes is 2^256 possible combinations.

#11 Token design: How its turned into text
Considered:
	Hex, Base64
Decision: Base64
Why:
	The primary reason I chose Base64 (URL-safe) over Hex is the length difference (43 vs 64).

#12 Token design: Hash Choice
Considered:
	SHA-256, Argon2ID
Decision: Sha-256
Why:
	Argon2ID is primarily for hashing user generated passwords which are short and repeated. Each token is 256 bits which is long and random. Argon2ID is also deliberately slow and memory hungry to slow the speed of guesses. SHA-256 is appropriate here because guessing a 256 bit token is unrealistic even with a machine guessing billions of combinations per second. 

#13 Token design: Structure
Considered:
	One class, Two classes
Decision: Two classes
Why:
	Even though they are connected, creating and hashing a token are two separate tasks. By separating the two into individual classes the purpose of each class is clear. Also when a user wants to see information about the shortened url we need to hash their token and compare it which has nothing to do with creating a token.

#14 Link Service: Retry strategy
Considered:
	3, 5, 10
Decision: 3
Why:
	7 characters of base62 creates ~3.52 trillion combinations. Collisions are statistically negligible at this scale. Even with millions of stored links, the probability of three consecutive collisions is approximately 1 in 40 quadrillion. Therefore if three consecutive attempts fail, it indicates an underlying system issue rather than bad luck. Capping retries at 3 allows the application to fail fast and avoid wasting database round trips. If retries are exhausted, an IllegalStateException is thrown.

#15 Link Service: Retry loop
Considered:
	for loop inside try-catch, try-catch inside for loop
Decision: try-catch inside for loop
Why:
	If the for loop was located inside the try block, any collision would immediately jump to the catch block which aborts subsequent retries. Placing the try-catch inside the loop isolates each attempt so a collision can be logged and the next iteration can proceed.

#16 Link Service: Transaction Boundary
Considered: method-level @Transactional vs per-operation transaction
Decision: Per-operation transaction
Why:
	In PostgreSQL and Spring Data JPA a unique constraint violation marks the transaction as aborted. This means if the entire service method was annotated with @Transactional, the first collision would poison the transaction and all subsequent attempts in the loop would fail with an aborted transaction error. By omitting @Transactional on the service method and using repository.saveAndFlush(), each attempt is its own isolated transaction managed by Spring Data JPA.
